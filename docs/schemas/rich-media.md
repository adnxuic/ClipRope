# Rich text and image codecs (version 1)

All formats below use content aspect and index -1. RTF and packed bitmaps use HGLOBAL. PNG supports HGLOBAL and bounded IStream content, including the stream form offered by Office. ClipRope records registered names and the saved medium, then resolves the Windows clipboard IDs again at publication. Native Office forms retain their individual manifest outcomes.

| Format | Retained subset |
| --- | --- |
| Rich Text Format | RTF version 1 with balanced groups, escaped braces, hexadecimal escapes and bounded binary runs. Group nesting is limited to 256. The self-contained byte stream, including its terminator, is limited to 8 MiB. The card preview never executes RTF fields or embedded objects. |
| PNG | Registered PNG bytes through IEND. The signature, IHDR bounds and chunk extents must be valid. The Windows PNG decoder must successfully materialize every scanline. |
| CF_DIB and CF_DIBV5 | Packed, uncompressed BGR24 and BGR32 in top-down or bottom-up order. Supported header sizes are 40, 108 and 124 bytes; CF_DIBV5 requires the 124-byte header. The 32-bit bitfield subset accepts standard red, green and blue masks and an optional full alpha byte. Palettes, unsupported masks, compressed bitmaps and embedded or linked color profiles are skipped when unusable. |

Each image is limited to 32 MiB of input, 8,192 pixels per side and 8,388,608 pixels overall. The adapter checks dimensions before decoding, verifies the row stride and payload length for packed images, and excludes allocator padding from the persisted bytes. Consumers receive the saved representation and medium after restart.

## Preview and restore details

The tray reads bounded text prefixes and manifest labels. Visible image cards can request a WIC preview on a lazy background worker. It scales to at most 320 × 256 pixels in premultiplied BGRA, a card's picture area at 200% scaling, and deduplicates requests by source hash and adapter. The worker accepts up to 16 queued jobs. The in-process preview cache has a 16 MiB byte cap and a 512-entry cap, including failed lookups. The shared Direct2D renderer retains up to 64 thumbnail bitmaps of that bounded size within 32 MiB. Each entry's snapshot identity guards bitmap reuse.

The profile's `thumbnails` directory contains rebuildable derivatives. Each file records a format version, dimensions and pixel checksum, with its source hash and image adapter in the filename. Pixel previews use `THM3` and file previews use `CRF2`. Both record oriented source dimensions. An obsolete header is a cache miss. With the source available, the worker decodes and replaces it. When the source is unavailable, only a current cached preview can supply pixels. The worker checks source reachability under the storage writer lock before installing a newly decoded file. Collection removes recognized orphan derivatives and interrupted thumbnail staging files. Sharing the image through either Hanging or Floating keeps its disk preview reachable. Removing a preview never changes a published format.

Choose **Card information…** on any card to review **Capture details** (Saved, Source and Capture), followed by **File health** for real file references, and **Capture inventory**. File health shows every Original path in saved order, preserving duplicate group members, then the aggregate File status and Preview. Single files include all three sections. Pixel screenshots and virtual files omit File health. File status describes the latest background availability result independently of Capture and format outcomes; an image decode failure affects Preview rather than file availability. A file with no image preview uses Not applicable. The inventory preserves format names, indices and individual saved, skipped, failed or damaged outcomes, including partial-capture notes.
